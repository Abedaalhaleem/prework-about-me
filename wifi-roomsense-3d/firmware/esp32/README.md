# RoomSense ESP32 firmware

This directory holds the device side of WiFi RoomSense 3D:

| Path | What it is |
|---|---|
| `roomsense_csi_rx/` | **Receiver.** Captures Wi-Fi CSI from one known transmitter and streams it over USB serial in the CRC-framed `roomsense-rscsi-v1` protocol ([`docs/SERIAL_PROTOCOL.md`](../../docs/SERIAL_PROTOCOL.md)). |
| `roomsense_csi_tx/` | **Transmitter.** Broadcasts a small ESP-NOW frame (the 12-byte `RSTX` payload) at a fixed, bounded rate. |
| `components/rs_csi_core/` | Platform-independent C11 core used by both apps: line formatters, CRC-32, hex, MAC parsing, the RSTX payload, ESP-NOW frame parsing and the rate schedule. It has no ESP-IDF includes and is unit-tested on the host. |
| `host_tests/` | Host unit tests for the core, plus the golden protocol lines the Python parser tests read. |
| `tools/` | `check_idf_env.sh` (pins ESP-IDF v5.5.5) and `header_syntax_check.sh` (a header-level check, not a build). |

The firmware covers **capability A only (CSI acquisition and diagnostics)**. It
does not detect motion, locate people or estimate pose. The host does any of
that, and only with the evidence gates described in `docs/ARCHITECTURE.md`.

## Provenance and licence

Both apps are derived from Espressif's
[esp-csi](https://github.com/espressif/esp-csi) `examples/get-started/`
(`csi_recv`, `csi_recv_router`, `csi_send`) at commit
`8633d67152db2808f141cc1595970aa9cf406045` (2026-04-22). Those sources carry
`SPDX-License-Identifier: Apache-2.0`, and the example text also says "This
example code is in the Public Domain (or CC0 licensed, at your option.)". The
file headers here keep that attribution. `rs_csi_core` and the host tests are
new code.

### What changed compared with upstream, and why

| Upstream get-started example | RoomSense | Why |
|---|---|---|
| Prints every CSI value with `ets_printf` *inside* the CSI callback | The callback only checks the MAC, copies the record into a bounded FreeRTOS queue (`xQueueSend(..., 0)`, it never blocks) and returns. A lower-priority printer task formats and writes the lines. | The ESP-IDF Wi-Fi guide says the CSI callback runs in the Wi-Fi task and must not do lengthy work. Printing ~1–4 KB per packet there stalls Wi-Fi. |
| Free-form CSV (`CSI_DATA,...`), no integrity check | `RSHELLO` / `RSCSI` / `RSSTAT` lines with a CRC-32 (the same as `zlib.crc32`), explicit `NA` for missing fields, sequence and drop counters | Interleaved or truncated lines are detected and rejected. Missing metadata is never guessed. Drops show up as sequence gaps. |
| MAC compared after the callback has started work | The MAC filter is the **first** thing the callback does. Frames from other devices are counted and never copied or parsed. | Privacy and CPU budget. |
| `esp_csi_gain_ctrl` gain compensation, values scaled into int16 | Raw `int8` values, no gain compensation, no managed components | The host sees exactly what `wifi_csi_info_t.buf` contained. |
| HT40 for ESP-NOW | **HT20** (secondary channel none) on both boards, ESP-NOW at HT20 MCS0 | The classic LLTF layout is then the documented "secondary channel none" row. HT20 also keeps the transmitter within 20 MHz. |
| Receiver sets its own MAC to the transmitter's `1a:00:00:00:00:00` | The receiver keeps its factory MAC and reports it in `RSHELLO` | Two stations with one MAC on air is wrong, and the host needs to know which board it is talking to. |
| `*(uint32_t *)(info->payload + 15)` read unconditionally | The ESP-NOW frame structure (category 127, OUI 18:fe:34 twice, element 221, type 4) and every length are checked first (`rs_espnow_body`), then the `RSTX` magic and version | No out-of-bounds read. A frame that is not ours gives `tx_seq = NA`, never garbage. |
| csi_send: bare `uint32` counter, `usleep` pacing, MAC set after `esp_wifi_start` | 12-byte `RSTX` payload, `xTaskDelayUntil` with an exact fractional schedule, MAC set before start (as the `esp_wifi_set_mac` docs require), locally administered MAC enforced | A steady, known rate. Local send failures are not confused with over-the-air loss (`seq` only advances on `ESP_OK`). |
| `nvs_flash_erase()` when NVS is full or from a newer format | Never erases. It stops and tells you the command to run yourself. | The firmware never erases flash on its own. |
| Router example leaves modem sleep on | `esp_wifi_set_ps(WIFI_PS_NONE)` on this board after connecting | `rx_ctrl.timestamp` is only precise without modem sleep. This changes only the ESP32, never the router. |

CSI acquisition settings are unchanged from upstream `csi_recv_router`, and
both modes use them:

* classic chips (ESP32, S2, S3, C3): `lltf_en=true, htltf_en=false,
  stbc_htltf2_en=false, ltf_merge_en=true, channel_filter_en=true,
  manu_scale=true, shift=1` (upstream writes `true`). Only the LLTF is captured,
  so every record has 128 values. `RSHELLO` reports `ltf_config=lltf_only`.
* ESP32-C5 / C61 and ESP32-C6: the upstream `wifi_csi_acquire_config_t`
  values, including `acquire_csi_legacy=true` and `acquire_csi_force_lltf=false`.
  `RSHELLO` reports `ltf_config=c5_default`.

## Supported targets

| Target | rx_ctrl type in v5.5.5 | Firmware branch | Host CSI layout support (`backend/roomsense/csi_layouts.py`) |
|---|---|---|---|
| esp32, esp32s2, esp32s3, esp32c3 | `wifi_pkt_rx_ctrl_t` | classic, `lltf_only` (128 values) | **Documented**: LLTF rows of the v5.5.5 table for secondary channel none/above/below |
| esp32c5 | `esp_wifi_rxctrl_t` (MAC v3) | `c5_default` | **Documented** C5 rows only: 106 / 114 / 234 / 490 values with an unambiguous order; anything else is rejected |
| esp32c6 | `esp_wifi_rxctrl_t` (MAC v2) | `c5_default` | **No layout table in the v5.5.5 guide.** The host rejects these frames unless the user opts into `allow_undocumented_layout_assumption`, and then every frame is flagged |
| esp32c61 | `esp_wifi_rxctrl_t` (MAC v3) | `c5_default` | Same as C6 (undocumented, opt-in assumption only) |

Other targets fail at compile time with an explicit `#error`.

On C5/C6/C61, `esp_wifi_rxctrl_t` has no `sig_mode`, `mcs`, `cwb`,
`smoothing`, `not_sounding`, `aggregation`, `stbc`, `fec_coding`, `sgi`,
`ampdu_cnt` or `ant`, so those fields are `NA`. `bb_format` carries
`cur_bb_format` and `secondary_channel` carries `second`. `rx_state` does exist
in that struct, but protocol v1 defines field 24 as classic-only, so it is also
`NA`. `agc_gain` and `fft_gain` are `NA` everywhere in v1. On these chips a
record whose `rx_ctrl.rx_channel_estimate_info_vld` is 0 is dropped as invalid
CSI (the v5.5.5 guide documents this bit for C5).

## Build (you run these; nothing here was compiled in the build container)

Install ESP-IDF **v5.5.5** yourself, following Espressif's getting-started
guide (for example `git clone -b v5.5.5 --recursive https://github.com/espressif/esp-idf.git`
followed by `./install.sh`). Then, from the repository root:

```bash
. $IDF_PATH/export.sh                      # activate ESP-IDF v5.5.5 in this shell

cd firmware/esp32/roomsense_csi_rx
../tools/check_idf_env.sh                  # refuses anything but v5.5.5 (RS_ALLOW_OTHER_IDF=1 to override)
idf.py set-target esp32s3                  # or esp32 / esp32s2 / esp32c3 / esp32c5 / esp32c6 / esp32c61
idf.py menuconfig                          # "RoomSense receiver": mode, channel, TX MAC, rate, queue
idf.py build

cd ../roomsense_csi_tx                     # the transmitter (ESP-NOW mode only)
../tools/check_idf_env.sh
idf.py set-target esp32s3
idf.py menuconfig                          # "RoomSense transmitter": channel, MAC, rate, tx_id
idf.py build
```

`idf.py set-target` creates a local `sdkconfig` from `sdkconfig.defaults`.
`sdkconfig`, `sdkconfig.old`, `build/` and `managed_components/` are
git-ignored.

**Router-mode credentials.** Router mode connects with ESP-IDF's
`protocol_examples_common` (`example_connect()`). Set the SSID and password in
`idf.py menuconfig` → *Example Connection Configuration*. They are then stored
only in the local, git-ignored `sdkconfig`. Never put them in
`sdkconfig.defaults` or commit them. The firmware only joins the network and
pings the gateway; it never changes router settings.

## Flash and monitor (commands for *you* to run, after you decide to)

The RoomSense app and its tools never flash, erase or reconfigure a board.
When you are ready, and with the right port, run:

```bash
idf.py -p /dev/ttyUSB0 flash               # writes this firmware to the board on /dev/ttyUSB0
idf.py -p /dev/ttyUSB0 monitor             # optional look at the output; the monitor follows the 921600 console baud
```

Close the monitor before starting the RoomSense host, because a serial port can
only be opened by one program. If the firmware reports that NVS is unusable
(often left over from other firmware), it stops instead of erasing anything.
Erasing (`idf.py -p PORT erase-flash`) is your decision.

## Serial settings

* UART0, **921600 baud, 8N1**. The console is the "Custom UART" choice, which
  is the only one where the baud rate can be set. `RSHELLO` field 15 reports
  the baud, or `NA` if you switch the console to USB-Serial-JTAG or USB CDC,
  where a baud rate has no meaning.
* Line endings: the formatter ends each line with `\n`, and ESP-IDF's default
  console conversion (`CONFIG_LIBC_STDOUT_LINE_ENDING_CRLF`) sends `\r\n`. The
  host strips the `\r`.
* ESP-IDF log lines (`I (123) rs_rx: ...`) share the port. The host treats them
  as diagnostics and never as data.
* On chips with a native USB-Serial-JTAG port (S3, C3, C5, C6, C61), ESP-IDF
  mirrors the console there by default (`CONFIG_ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG`).
  Connect the host to the board's **USB-UART bridge** port. If the native USB
  port is also plugged in but nobody reads it, ESP-IDF can wait up to 50 ms per
  write before dropping that copy (`TX_FLUSH_TIMEOUT_US` in
  `usb_serial_jtag_vfs.c`), which slows the printer. Set
  `CONFIG_ESP_CONSOLE_SECONDARY_NONE=y` if that matters to you. This is not
  changed by default because some boards only have the native port.

## Throughput (computed, not measured)

UART 8N1 carries 10 bits per byte, so 921600 baud is at most **92 160 bytes/s**.
Line sizes below are the real output of the C formatter from the host tests
(`test_rs_csi_core` prints them), plus 1 byte for the `\r`:

| Line | Bytes on the wire | Upper bound, lines/s at 921600 |
|---|---:|---:|
| RSCSI, classic, len 128, small counters | 370 | 249 |
| RSCSI, classic, len 128, 10-digit counters | 378 | 243 |
| RSCSI, ESP32-C5 HT20, len 114 | 347 | 265 |
| RSCSI, ESP32-C5 HE20, len 490 (estimate: 114-value line + 2×376 hex) | ≈1099 | ≈84 |
| RSCSI, len 612 (largest documented buffer) | 1353 | 68 |
| RSCSI, absolute worst case (every field at maximum width) | 1563 | 59 |
| RSSTAT (every 1 s) / RSHELLO (every 5 s) | 66–102 / 136–145 | about 130 bytes/s together |

At the default 25 Hz with 128-value records the load is about **9.6 kB/s, or
about 10% of the link**. The bounds above are theoretical. The printer also
sleeps one tick after every 16 consecutive lines, so the idle task (which the
task watchdog watches) always gets CPU time. That costs at most about 1.5% at
the maximum rate. Without the UART driver installed, the ESP-IDF console
busy-waits on the UART FIFO, so the printer task is busy for each line's wire
time: about 4 ms per 378-byte line, or about 10% CPU at 25 Hz. It runs at
priority 4, below the Wi-Fi task (23), lwIP (18) and the ping task (5).
**The host measures and reports the rate it actually receives.** Use that, not
this table.

If the serial link cannot keep up, the queue (`RS_QUEUE_DEPTH`, default 32
records × 736 bytes ≈ 23.5 KB of RAM, about 1.3 s of backlog at 25 Hz) fills.
New records are then dropped and counted in `dropped_queue_full`. They are
never truncated and never block the Wi-Fi task.

## Counters, sequence numbers and rollover

* `rec_seq` (RSCSI field 2) advances once for every callback that passed the
  MAC filter, *before* any drop decision. Every device-side drop (queue full,
  oversize, invalid CSI) is therefore a visible gap.
* `drops` (field 4) is `dropped_queue_full + dropped_oversize` so far. Gaps not
  explained by `drops` are serial-link loss (or, on C5/C6/C61, invalid-CSI
  drops; see below).
* `tx_seq` (field 3, ESP-NOW mode) comes from the transmitter. Gaps are
  over-the-air loss. It is not authenticated, so treat it as a diagnostic.
* `RSSTAT`: `cb_total`, `cb_filtered`, `enqueued`, `dropped_queue_full`,
  `dropped_oversize`, `printed` (RSCSI lines fully written), `tx_ok` and
  `tx_fail` (router mode: ping replies and timeouts; `NA` in ESP-NOW mode),
  `free_heap` and `min_free_heap`. With an empty queue,
  `cb_total = cb_filtered + cb_invalid_arg + enqueued + dropped_queue_full + dropped_oversize + dropped_invalid_csi`.
  The two counters protocol v1 has no field for (`cb_invalid_arg`,
  `dropped_invalid_csi`), plus serial `write_errors` and `format_errors`, are
  logged as an `ESP_LOGW` diagnostic line every 10 s while any of them is
  non-zero.
* Every counter is u32 and wraps at 2^32. `rx_timestamp_us` wraps about every
  71.6 minutes. The host unwraps all of them. `uptime_ms` is u64.

## ESP-NOW mode details

* Both boards use STA mode, the same fixed channel (`RS_CHANNEL`, default 11,
  must match), HT20 and no power save. The receiver runs promiscuous (as
  upstream does) with no promiscuous RX callback. Only the CSI callback sees
  frames, and it discards everything not from `RS_TX_MAC`.
* The transmitter sends ESP-NOW broadcasts at HT20 MCS0 (long GI). The ESP-NOW
  default rate is 1 Mbps DSSS, whose frames have no OFDM training fields and
  therefore no LLTF CSI.
* The transmitter's MAC (`RS_TX_MAC`, default `1a:00:00:00:00:00`, as in
  csi_send) must be unicast and locally administered. The firmware refuses
  anything else, so it can never copy a vendor-assigned address.
* `tx_seq` extraction assumes `wifi_csi_info_t.payload` starts after the
  24-byte MAC header (upstream reads `payload + 15`, which matches the v5.5.5
  ESP-NOW frame format). Because every structural byte is checked, a wrong
  assumption shows up as `tx_seq = NA`, not as wrong numbers. **Not verified on
  hardware.**

## Router mode details

* The board joins your own AP with `example_connect()`, reads the AP's BSSID
  once, and exports CSI only from frames sent by that BSSID. It pings the
  gateway at `RS_RATE_HZ`. The interval is `1000 / RS_RATE_HZ` whole
  milliseconds, so 25 Hz is exactly 40 ms and 30 Hz is 33 ms (30.3 Hz). The
  ping timeout equals the interval, so a lost reply does not stall the
  schedule.
* If the station later reconnects to a different BSSID (roaming or mesh
  networks), every frame is filtered out. `RSSTAT` then shows `cb_filtered`
  rising while `enqueued` stays flat. Reboot the receiver in that case.
* The AP decides its own bandwidth. With HT40 the LLTF order follows the
  "secondary channel above/below" rows, which the host handles.

## Host-side tests and tools

```bash
make -C firmware/esp32/host_tests test            # unit tests (+ ASan/UBSan when available)
make -C firmware/esp32/host_tests golden          # rewrite golden_rscsi_lines.txt / golden_rscsi_expected.jsonl
make -C firmware/esp32/host_tests verify-golden   # independent re-check with python3 zlib.crc32
make -C firmware/esp32/host_tests strict cross    # extra warnings; rv32imc clang compile of the core
```

* `host_tests/golden_rscsi_lines.txt` holds 12 **synthetic** machine lines
  written by the C formatter: RSHELLO (classic, router before connect, C5),
  RSCSI (len 128, 114 and 612, negative int8 values, `NA` fields, `rec_seq`
  at 2^32−2, 2^32−1 and 0 after the wrap), and RSSTAT (u64 uptime, counters at
  their wrap point). `golden_rscsi_expected.jsonl` lists the input values for
  each line (`NA` becomes `null`) so the Python parser can be checked field by
  field. `make test` fails if the committed golden file no longer matches the
  formatter.
* `tools/header_syntax_check.sh` needs `IDF_PATH` (v5.5.5), `RS_NEWLIB_INCLUDE`
  (`newlib/libc/include` of espressif/newlib-esp32 tag `esp-4.3.0_20260121`),
  optionally `RS_LWIP_SRC` (esp-lwip `fd432e4e…`; it defaults to the v5.5.5
  submodule), a Python with `esp-idf-kconfig`, and clang. It is useful only
  where no ESP toolchain is available. With ESP-IDF installed, run
  `idf.py build`.

## Known limitations

* Not compiled for any target and not run on hardware (see STATUS).
* Xtensa targets (ESP32, S2, S3) were not covered by the header-level check,
  apart from the Wi-Fi type members. Only a real `idf.py build` can confirm
  them.
* C5/C61 `lltf_bit_mode` is left at the upstream value (0, "12-bit"). The
  v5.5.5 table documents 8-bit-per-component sizes for the non-forced LTFs used
  here. The host accepts only those documented lengths.
* One transmitter per receiver. Several receivers can listen to one
  transmitter; each is a separate serial link on the host.
* The RSTX payload is plaintext and unauthenticated, so another device could
  spoof it. The MAC filter plus `tx_seq` only help with diagnosis.

## Privacy and safety

Use this only in spaces you control, and only with the consent of the people
present. The firmware exports CSI only from the one configured transmitter or
AP, sends everything over the local USB serial link, has no network uploads,
and stores no credentials in the repository. Motion sensing through a wall is
experimental. A 3-D view on the host is a visualisation, not proof of 3-D
reconstruction.
